Orquestador local de agentes IA con ruteo adaptativo

Sistema de ciclo cerrado para optimización de inferencia multi-proveedor mediante enrutamiento semántico, recuperación aumentada y retroalimentación acumulativa de ejecuciones previas.

Python 3.10+ SQLite WAL + ChromaDB MCP · SSE · Typer Claude · OpenAI · DeepSeek Uso local · MIT License
§ 1
Resumen

¿Qué propone este sistema?

Los flujos de trabajo modernos de desarrollo con IA involucran múltiples proveedores con capacidades y costos distintos. La práctica habitual es elegir un proveedor por defecto o alternar manualmente según la tarea — ambas estrategias dejan valor sobre la mesa: o se paga por capacidad innecesaria, o se infrautiliza el modelo correcto para el problema.

ai-orchestrator es un proceso local que actúa como intermediario inteligente entre las tareas de desarrollo y los proveedores de IA. Implementa un ciclo de enrutamiento adaptativo donde cada decisión de ruteo es informada por el contexto semántico del proyecto, las ejecuciones anteriores similares y sus calificaciones explícitas de calidad.

Estado — Infraestructura completa. Ciclo de aprendizaje en activación. Versión — production · junio 2026 Licencia — MIT Autor — Carlos Santis

Contribuciones principales

Ruteo semántico de bajo costo

Un modelo de $0.14/M tokens (DeepSeek Flash) analiza la tarea, el stack del proyecto y señales de runs previos para elegir proveedor y tier de modelo — sin intervención manual.

Ciclo de feedback por ratings

Cada run puede calificarse como útil, parcial o erróneo. Las calificaciones se inyectan como señal contextual en decisiones futuras similares, sin reentrenamiento ni MLOps.

RAG aplicado al router

ChromaDB indexa docs del proyecto y respuestas previas. El contexto recuperado informa a quién se manda la tarea, no solo cómo se responde — RAG en la capa de decisión.

Observabilidad integrada

Dashboard web con SSE, barra de actividad con spans en tiempo real, Inspector de estado interno, panel de efectividad RAG y tracking de costo acumulado por proyecto.

Integración con agentes externos

Servidor MCP (JSON-RPC 2.0) permite que Claude Code consuma el orquestador directamente. Importadores de sesiones CC y Codex unifican el historial de todos los agentes.

Sustrato mínimo

Sin frameworks de orquestación externos. SQLite como única base de datos. Vanilla JS en el frontend. Dependencias intencionalmente reducidas para maximizar longevidad y portabilidad.

Fuera del alcance

  • No es un proxy de API — el proceso debe estar corriendo localmente; no es un servicio cloud.
  • No orquesta agentes en paralelo — una tarea a la vez por run; el paralelismo es trabajo futuro.
  • No gestiona conversaciones — cada run es stateless salvo el contexto RAG inyectado.
  • No tiene autenticación — está diseñado para uso local en un entorno de desarrollo personal.
§ 2
Motivación

El problema de ruteo en entornos multi-proveedor

La proliferación de modelos de lenguaje con capacidades complementarias — y precios muy distintos — genera un problema de asignación: dado un tipo de tarea, ¿qué modelo maximiza la relación calidad/costo? La respuesta varía por proyecto, por tipo de tarea, por el historial de lo que funcionó, y cambia a medida que los modelos evolucionan.

Las estrategias de ruteo habituales y sus problemas

EstrategiaProblema
Proveedor fijo por defectoSe paga por capacidad innecesaria en tareas simples; o se infrautiliza el modelo correcto en tareas complejas.
Alternancia manual por tareaRequiere contexto mental del desarrollador en cada run. No escala. No aprende de errores pasados.
Reglas estáticas por keywordFrágil ante variaciones de redacción. No captura similitud semántica. No incorpora retroalimentación.
Delegar a un modelo caro la decisiónEl costo del router supera el beneficio del ahorro. Contradice el objetivo.

Por qué los frameworks generales no resuelven el caso local

Existen herramientas establecidas para orquestación de LLMs. Cada una resuelve un problema distinto al que aborda este sistema:

HerramientaEnfoqueDiferencia con ai-orchestrator
LangChain RouterEnrutamiento entre chains definidas por el desarrollador. Framework-heavy.No tiene ciclo de feedback local. Requiere definir los destinos explícitamente. Sin tracking de costo ni historial persistente.
AutoGenConversaciones multi-agente con roles definidos.Orquestación conversacional, no de tareas puntuales. No selecciona proveedor por costo/complejidad. Sin RAG en la decisión de ruteo.
LlamaIndex RouterQueryEngineEnrutamiento entre fuentes de datos (RAG).Ruta entre índices, no entre proveedores. Sin historial de ejecuciones ni feedback loop.
OpenRouterProxy cloud que agrega múltiples providers bajo una API.Servicio externo — toda la tarea pasa por un tercero. Sin persistencia local, sin contexto de proyecto, sin feedback.
Semantic RouterClasificación de intenciones para enrutar prompts.Solo clasifica texto de entrada; no considera historial, costo, contexto de proyecto ni feedback de ejecuciones previas.
El gap: ninguna de estas herramientas implementa un ciclo donde la calidad observada de ejecuciones previas retroalimenta la decisión de ruteo futura para tareas similares del mismo proyecto — sin reentrenamiento y con costo de routing cercano a cero.

El costo real de no orquestar

Los datos del sistema sobre proyectos propios ilustran el problema. En el período de registro, el gasto en sesiones de Claude Code y Codex ejecutadas fuera del router acumuló $344 USD. Los 18 runs ejecutados a través del router costaron $0.026 USD en total — $0.0014 por run en promedio. La diferencia no es un ahorro directo (son distintos tipos de tarea), sino evidencia de la magnitud del gasto que ocurre sin ningún mecanismo de optimización.

§ 3
Postulado

Propuesta central e hipótesis verificables

Un sistema de orquestación local de agentes IA puede optimizar la relación calidad/costo de inferencia mediante un ciclo adaptativo de tres componentes: (1) enrutamiento semántico de bajo costo que selecciona proveedor y tier de modelo según contexto del proyecto, (2) recuperación semántica aumentada que inyecta contexto documental y de ejecuciones previas en la decisión de ruteo, y (3) retroalimentación explícita por ratings que pondera las señales de runs similares. El ciclo requiere volumen mínimo de runs autónomos para producir señal útil — la infraestructura puede construirse antes, pero el aprendizaje comienza cuando el router toma decisiones sin intervención manual.

Hipótesis derivadas

H1 — Eficacia del router económico
Un modelo de $0.14/M tokens con contexto semántico suficiente produce decisiones de ruteo correctas — medido por la tasa de runs con rating useful vs wrong en runs donde el router decidió de forma autónoma.
Métrica: % runs autonomos con rating=useful / total runs autonomos calificados
H2 — Mejora por feedback acumulativo
La tasa de runs calificados como erróneos disminuye a medida que el historial de ratings crece — sin reentrenamiento del modelo router ni intervención manual en las reglas de ruteo.
Métrica: tasa_wrong por ventana temporal de 20 runs (tendencia decreciente)
H3 — Valor del RAG en el router
Los runs donde el router recuperó contexto RAG relevante (context_hits > 0) tienen mayor tasa de rating useful que los runs sin hits — verificando que RAG en la capa de decisión agrega señal más allá de las keywords estáticas.
Métrica: useful_rate(runs con hits) vs useful_rate(runs sin hits)

Condición de activación del ciclo

Las tres hipótesis requieren que el router tome decisiones autónomas. Mientras el usuario especifica el provider con --model, el router no decide — acumula datos de costo y tokens pero no genera señal de calidad. El ciclo de aprendizaje arranca cuando:

  • Al menos 20 runs son ejecutados sin override de provider
  • Al menos 10 de esos runs reciben una calificación (útil / parcial / erróneo)
  • Los runs provienen de al menos 2 proyectos distintos con contexto.yaml configurado
Estado actual: La infraestructura del ciclo está completa. Los 18 runs via router registrados hasta junio 2026 fueron todos con override manual (routing_reason = "Elegido manualmente"). El rating de todos los runs es null. El ciclo está en fase de activación.

§ 5
Técnicas

Técnicas implementadas por categoría

Las decisiones de implementación se agrupan en seis categorías funcionales. Cada técnica responde a una restricción concreta del entorno local: sin servidor central, sin MLOps, con dependencias mínimas, con múltiples threads concurrentes.

5.1 — Persistencia y recuperación eficiente

TécnicaDóndePor qué
SQLite WAL modedb.pyPermite lecturas concurrentes sin bloquear escrituras. El handler SSE puede leer mientras el worker thread escribe un run simultáneamente.
FTS5 virtual tables + triggersdb.py schemaFull-text search sobre runs.task sin índice manual. Los triggers INSERT/UPDATE/DELETE mantienen el índice sincronizado automáticamente.
Thread-local DB connectionsdb.py:threading.local()Cada hilo (HTTP handler, worker thread, MCP server) mantiene su propia conexión SQLite para evitar contención y errores de thread-safety.
Migraciones monotónicasmigrate.py + _migrationsTabla de control con flag de aplicación. Cada migración es idempotente, se aplica exactamente una vez — sin ORM, sin downtime, sin rollback necesario.
UNIQUE constraint session_idruns.session_idImportaciones repetidas de la misma sesión CC o Codex son ignoradas por constraint de SQLite, sin lógica adicional en Python. Deduplicación a costo cero.

5.2 — Recuperación semántica aumentada (RAG)

TécnicaDóndePor qué
Embeddings locales (all-MiniLM-L6-v2)rag.py · ChromaDBModelo de embeddings que corre en CPU local. Sin llamadas a APIs externas, sin costo por indexación, sin datos del proyecto que salgan del equipo.
Overlap chunking (1500 / 200 chars)rag.py:_chunk()Chunks de 1500 caracteres con 200 de overlap. El overlap preserva contexto en los bordes — una función o bloque que atraviesa el límite queda representado en ambos chunks.
Umbral de similitud L2=0.9rag.pyEquivale a cosine_similarity ≥ 0.60 aproximadamente. Filtra ruido semántico: un chunk que no es lo suficientemente similar no contamina el contexto del router.
FTS5 fallbacksimilarity.py:FTS5BackendDegradación elegante cuando ChromaDB no está instalado. El sistema sigue funcionando con búsqueda por keywords — sin cambios en la interfaz de llamada.
Secret pattern detectionrag.py:_has_secrets()Regex aplicado sobre el contenido de cada archivo antes de indexar. Archivos con patrones de API keys, tokens o claves privadas se omiten del índice RAG.
RAG en la capa de routingrouter.py:_fetch_similar_runs()El contexto recuperado no solo enriquece el prompt del provider — informa la decisión de a quién se manda la tarea. RAG en la capa de decisión, no solo de ejecución.

5.3 — Router adaptativo

TécnicaDóndePor qué
One-shot con modelo económicorouter.py · DeepSeek Flash$0.14/M tokens vs $3+/M del provider ejecutor. La decisión de ruteo representa <5% del costo total de un run típico.
Keyword hints pre-LLMcontext.py:keyword_hintsSeñales léxicas calculadas en Python antes de llamar al router. Enriquecen el prompt con pesos por topic ("seguridad → claude weight:3") sin sustituir la decisión semántica.
Rating feedback looprouter.py:_build_router_prompt()Runs similares recuperados de ChromaDB incluyen su rating. El prompt del router recibe etiquetas [ÚTIL] / [ERRÓNEO — evitar para este tipo de tarea] que ajustan la decisión sin fine-tuning.
Context compressionrouter.py:_compress_context()Si las convenciones del proyecto superan un umbral de caracteres, se filtran solo las más relevantes para la tarea. Evita superar el context limit del router económico.
Model tier selectionrouter.py:RoutingDecision.modelEl router devuelve no solo el proveedor sino también el tier de modelo (Haiku para tareas simples, Sonnet/Opus para complejas). La selección de tier es parte de la optimización de costo.
Step provider enforcementcli.py:submit_run()Si hay un paso activo en el contexto de trabajo con un provider sugerido, el router respeta esa restricción. El contexto de planificación tiene precedencia sobre la decisión semántica.

5.4 — Observabilidad en tiempo real

TécnicaDóndePor qué
SSE fan-out pub/subsse.py:SSEBusCola independiente por suscriptor (maxsize=100). Si el browser es lento, la queue se descarta sin bloquear al publicador ni afectar otras conexiones. O(n) por suscriptor.
Span tracingtracer.py:span()Context manager que mide duración de cada operación (Router, RAG, API call, Index) y emite eventos al SSE bus. La barra de actividad del dashboard consume estos spans.
Budget trackingdb.py + dashboard.pyCosto acumulado del día vs presupuesto diario definido en config.yaml. Gauge visual + alerta SSE al cruzar el threshold configurado.
RAG effectiveness paneldb.py:read_inspector_data()Porcentaje de runs con al menos un context_hit por proyecto. Hace visible si el RAG está produciendo señal útil o si el índice necesita actualizarse.

5.5 — Integración con agentes externos

TécnicaDóndePor qué
MCP server (JSON-RPC 2.0 stdio)mcp_server.py · 11 toolsProtocolo estándar de Model Context Protocol. Claude Code puede consumir el orquestador sin configuración adicional más allá de registrar el servidor.
CLAUDE.md auto-generadocontext.py:create_claude_md()Al registrar un proyecto, el orquestador escribe un CLAUDE.md con instrucciones para que Claude Code invoque las herramientas MCP al inicio de cada sesión. Reduce la fricción de onboarding a cero.
Session importers (CC + Codex)watcher.py · codex_watcher.pyImportan sesiones de Claude Code y Codex al historial unificado. UNIQUE constraint en session_id garantiza idempotencia. Las sesiones importadas se vinculan al paso activo del contexto de trabajo.

5.6 — Patrones estructurales

Factory

providers/factory.py — instancia el provider correcto a partir del nombre en config. El resto del sistema recibe un objeto con interfaz uniforme, sin saber qué proveedor es.

Strategy + Protocol

similarity.py:SimilarityBackend — interfaz @runtime_checkable. ChromaBackend y FTS5Backend son intercambiables sin herencia; basta con implementar upsert() y query().

Observer

sse.py:SSEBus — fan-out de eventos a todos los suscriptores activos. El publicador no conoce a los suscriptores; cada conexión /events recibe una queue independiente.

Repository

db.py — abstrae SQLite del resto del sistema. El código llama a insert_run(), read_runs() sin conocer SQL, paths de archivo, ni el modo WAL.

Template Method

providers/base.py:BaseProvider — contrato abstracto complete(prompt, system) → CompletionResult. Cada provider implementa solo la diferencia: headers, endpoint, parsing de tokens.

Duck typing estructural

similarity.py — Python Protocols como interfaz estructural. No hay herencia de clases concretas. El sistema acepta cualquier objeto que implemente el protocolo, sin importar su origen.

Limitaciones

Limitaciones conocidas

Limitaciones de diseño

LimitaciónImpactoDecisión de diseño
Una tarea a la vezNo puede ejecutar runs en paralelo. Tareas largas bloquean el worker thread.Simplicidad sobre throughput. El paralelismo requeriría un pool de workers y sincronización de DB más compleja.
Runs stateless (sin historial de conversación)Cada run es independiente — no hay memoria de turnos anteriores dentro de un run.El orquestador gestiona selección de proveedor, no conversaciones. El historial de sesiones está en CC/Codex.
Sin autenticación en el dashboardCualquiera con acceso a la red local puede ver el dashboard y ejecutar tareas.Diseñado para uso local personal. Agregar auth añadiría fricción sin beneficio en ese contexto.
El router depende de la calidad del modelo económicoSi DeepSeek Flash produce una decisión incorrecta, no hay segundo intento — va directamente al provider equivocado.El fallback_provider en config.yaml actúa si el provider elegido falla. Las malas decisiones se corrigen via ratings.

Limitaciones del ciclo de aprendizaje

LimitaciónConsecuencia
El ciclo requiere runs autónomos para arrancarMientras el usuario usa --model, el router no genera señal de calidad. La infraestructura existe pero no aprende.
Rating es manualEl usuario tiene que calificar los runs explícitamente. Sin ratings, el feedback loop no tiene señal.
RAG hit rate actual: 0%576 chunks indexados, pero 0 context_hits — los runs via router fueron todos manuales y el sistema no ejercitó la recuperación de contexto de forma autónoma aún.
Sin evaluación automática de respuestasNo hay mecanismo para evaluar la calidad de una respuesta sin intervención humana. El feedback es cualitativamente binario (útil / erróneo).

Limitaciones operativas

  • Requiere proceso activo: el orquestador debe estar corriendo (serve) para aceptar tareas. No hay cola persistente que sobreviva a un reinicio.
  • ChromaDB en CPU: la indexación de proyectos grandes puede ser lenta en máquinas sin GPU. Los embeddings son locales pero no acelerados por hardware.
  • config.yaml sin cifrado: las API keys se almacenan en texto plano en ~/.ai-orchestrator/config.yaml. La seguridad depende de los permisos del sistema de archivos.
§ 8
Trabajo futuro

Próximos pasos e investigación abierta

Inmediato — activar el ciclo de aprendizaje

El primer bloque de trabajo futuro no es código nuevo — es uso del sistema tal como está:

  • Ejecutar al menos 20 runs sin --model override para que el router tome decisiones autónomas
  • Asignar ratings (útil / parcial / erróneo) a esos runs desde el dashboard
  • Medir si la tasa de wrong disminuye con el historial creciendo — validación de H2
  • Verificar que context_hits aumenta cuando el router opera sin override — validación de H3

Corto plazo — mejoras al ciclo

  • Rating sugerido automático: comparar la respuesta del provider con la descripción de la tarea usando un modelo liviano — pre-poblar el rating para que el usuario solo confirme o corrija
  • Panel de comparación de providers: para un tipo de tarea dado, mostrar historial de qué provider fue elegido y cuál fue su rating — visualización directa de H1
  • Alertas de drift: si un provider que antes era ÚTIL empieza a producir ERRÓNEO en el mismo tipo de tarea, notificar al usuario

Mediano plazo — escala y colaboración

  • Paralelismo de runs: pool de worker threads con cola persistente en SQLite. Permite ejecutar varias tareas simultáneamente sin bloquear el dashboard
  • Modo equipo: compartir el DB entre múltiples instancias (SQLite WAL ya lo soporta en red local) para que ratings de distintos usuarios alimenten el mismo ciclo
  • Exportación de modelo de routing: si el historial de ratings es suficiente, entrenar un clasificador local que reemplace al LLM router para tipos de tarea recurrentes

Investigación abierta

  • ¿Cuántos runs calificados son necesarios para que el feedback produzca una mejora estadísticamente significativa en la tasa de decisiones correctas?
  • ¿El umbral de similitud RAG óptimo varía por tipo de proyecto (PHP vs Python vs JS)?
  • ¿El rating por run es suficiente señal o se necesita rating por fragmento de respuesta (partial credit)?
§ 9
Conclusión

Conclusión

El sistema implementa todos los componentes necesarios para el ciclo de enrutamiento adaptativo postulado: un router económico de un solo paso, recuperación semántica de contexto documental y de ejecuciones previas, retroalimentación por ratings, y observabilidad completa del estado interno.

Los datos del período de uso (febrero 2025 — junio 2026) confirman que la infraestructura funciona: $344 USD en actividad rastreada a través de 6 proyectos, 576 chunks indexados, 14 contextos con 62 pasos gestionados, y un costo por run via router de $0.0014 USD promedio — validando que el router económico es viable como capa de decisión.

Lo que los datos también revelan con claridad es la condición necesaria que el postulado anticipa: el ciclo de aprendizaje requiere runs autónomos. Mientras el usuario especifica el provider con --model, el router acumula datos de costo pero no genera señal de calidad. El feedback loop, el RAG hits y el step linkage están implementados y funcionan — pero aún no han sido ejercitados en condiciones autónomas.

El siguiente capítulo de este estudio es operacional: ejecutar el ciclo, medir, y evaluar si las tres hipótesis se sostienen con datos reales.

Un sistema de orquestación local puede construir su ciclo de aprendizaje antes de que ese ciclo tenga datos — y esa infraestructura pre-construida es precisamente lo que hace posible que el aprendizaje arranque sin fricción cuando las condiciones se dan.

ai-orchestrator run --project mi-proyecto --task "..." --research
Nota sobre el ciclo de aprendizaje: usar --model bypasea el router. Para que el feedback loop funcione, ejecutar runs sin especificar provider — dejar que el router decida.
